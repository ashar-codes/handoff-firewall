# Implementation decisions

1. **Explicit state graph.** The PRD permits LangGraph or a typed state machine. A small explicit graph keeps domain rules inspectable and avoids an unnecessary framework/runtime dependency. Six product responsibilities remain distinct functions and real event sources.
2. **Deterministic orchestration and verification.** Most first-release next steps can be chosen from observed state. The LLM extracts uncertain source candidates and drafts clarification language. It does not perform arithmetic, authorization or clearance. This is bounded agentic repair, not an unconditional six-prompt pipeline.
3. **One commercial wedge.** Sales → Finance order readiness supplies sample policies and scenarios; the policy engine is configurable across teams. Real commercial effectiveness still requires one customer's historical cases.
4. **Relational sources and actions, materialized statuses.** Requirement states are a persisted JSON map tied to rule/evidence versions; documents, facts, actions, approvals and events are relational entities. This is easier to inspect than opaque conversational memory.
5. **Conservative approvals.** Any material case revision invalidates approvals even where narrower dependency binding could preserve them. Unrelated waiting internal requests are retained to avoid repeated outreach. Tightening the approval dependency set requires customer-specific validation.
6. **Finite repair heuristic.** Search first, skip requests for facts blocked only by dependencies, calculate needed prerequisite closure, bundle by owner/action kind, and rank transparent effort values. No mathematical optimality or fabricated information-gain probability is claimed.
7. **Evidence acceptance.** Exact key/value matching follows configured field aliases. Natural-language extraction and human replies are candidates until a reviewer accepts them. Requirements may demand human review even for exact fields. Explicit human source precedence is recorded; version counters from unrelated documents cannot establish precedence.
8. **No speculative integrations.** Internal requests and approved external drafts are real persisted actions. External delivery and source-system writes are deferred until a real connector and reconciliation contract can be tested. The UI says nothing was sent.
9. **Local models only by default.** Ollama supports JSON schemas. An OpenAI-compatible local adapter is available; provider-specific transport stays in one module. Consumer development subscriptions are not API entitlements. The test fixture cannot run in development/production as a fallback.
10. **SQLite tests, PostgreSQL product.** Disposable SQLite supports inexpensive deterministic and browser scenarios. PostgreSQL-specific checks use an isolated target. In this environment PGlite supplied PostgreSQL-compatible SQL/migration checks; it does not prove real PostgreSQL concurrency.
11. **Same-origin cookie auth.** The web proxy forwards `/api`; native development uses the Vite proxy. Exact Origin checks and CSRF tokens protect mutations. No session token is placed in localStorage.
12. **Relative file keys.** Files are addressed beneath a private store rather than host-specific absolute database paths, enabling moves/restores. Original bytes must still match their recorded hash before verification.
13. **UI implementation.** React/Tailwind with shadcn-style Radix primitives, Lucide icons and XYFlow. No motion library was added because the operational experience does not need animation. Agent graph edges represent actual dispatch events; the chronological trace represents execution order.
14. **Release scope.** This is the R0/R1 production-structured core, with sample R2 workflow configuration and connector boundaries. Enterprise SSO, comprehensive retention, numerical tolerances, source-type precedence DSL, OCR, semantic retrieval and production operations are intentionally deferred and documented; there are no fake integration success paths.

15. **Full final verification.** Incremental evaluation is an efficiency aid, not proof of readiness. Recompute all rules at the READY boundary and allow authorized integrity rechecks of READY cases.
16. **One field grammar.** Source invalidation and exact extraction share a parser. Escape structured cell boundaries and reject ambiguous duplicate keys/headers instead of manufacturing or silently discarding facts.
17. **Claim fencing and atomic steps.** Keep the existing database worker, add generation/lease checks at commits/finalization, use consistent lock ordering, and roll back failed specialist writes. No new queue service is necessary.
18. **Human decisions remain explicit.** Reject is distinct from pending. Contradictory candidates need review. Partial replies retain unanswered requests. Add migration 0003 for evidence decisions and explainable conflict history without rewriting prior migrations.
19. **Dependency update exception.** Upgrade development-only Vitest 3.2.7 to 4.1.11 because GHSA-82fw-gwwq-j7x9 affects its mocker dependency; retain the application framework versions and lockfiles. Typecheck, lint, unit tests and build validate the change. See https://github.com/advisories/GHSA-82fw-gwwq-j7x9 for affected conditions; this was not evidence of application production exploitability.
20. **Safe restore rehearsal.** A flag named disposable-target was insufficient protection. Create a new database and separate file destination rather than restoring over configured application data.
21. **PRD scope honesty.** These repairs strengthen the R0/R1 core. R2 customer evaluation, R3 delivery connectors and R4 enterprise operations are not completed by passing fixture tests.
